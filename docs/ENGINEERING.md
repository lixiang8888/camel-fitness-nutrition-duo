## 一、CAMEL 架构

用的是 CAMEL 论文里的 `RolePlaying` 结构：一个负责产出内容的 assistant agent，
配一个负责提要求和挑刺的 user agent，各自带着自己的 system message 互相对话。

```
                    ┌──────────────────────────────────────┐
                    │   RolePlaying (camel.societies)      │
                    └──────────────────────────────────────┘
                                    │
             init_chat(opening)     │      step() × rounds
                    ┌───────────────┴───────────────┐
                    ▼                               ▼
        ┌────────────────────┐          ┌────────────────────┐
        │  assistant_agent   │          │    user_agent      │
        │  营养师 · 循证派   │  ──────▶ │   教练 · 实战派    │
        │ system_message =   │  ◀────── │ system_message =   │
        │  人格 + 本次议题   │          │  人格 + 本次议题   │
        └────────────────────┘          └────────────────────┘
                    │                               │
                    └───────────────┬───────────────┘
                                    ▼
                      TopicTranscript（逐条发言记录）
                                    │
                                    ▼
                      digest（整理环节，非智能体）
                                    │
                                    ▼
                     transcript-*.md  +  handbook-*.md
```

**流程**：6 个议题 → 每个议题跑一次 `RolePlaying`（默认**最多** 3 轮）→ 对话实录落盘 →
整理成手册章节 → 拼装成最终手册。

议题表见 `src/fitness_duo/topics.py`，每个议题都对应手册的一节。
选题标准：**如果两人对这个议题天然意见一致，就不该收进来。**

轮数是**上限**不是定额：教练提不出新的反对意见时该议题提前收手（见下一节）。

### 自适应轮数：什么时候提前收手

**camel 在这件事上什么都没规定**——`RolePlaying.step()` 是**一轮一调**，内部不含循环、
也没有 `max_turns`，跑几轮完全由调用方决定。所以「跑满 N 轮」是 `society.debate_topic`
自己那个 `for` 循环，收手也在这里。

判据不在代码里猜，而是**让挑战者自己表态**：

- `personas.COACH` 多了一条纪律：对当前方案**没有任何新的反对意见**时，只回复一句
  `【无异议】`；只要还有一条没提过的意见就必须继续提。
- `society._is_concession()` 看到这句话就收手。**判定用完全相等，不是包含**——
  模型要是写了「【无异议】不过还有两点」，那说明它其实还有话说，这里就当没看见、
  让辩论继续。两个方向的错代价差得很远：漏判只是多花一轮的钱，误判会把一整段
  发言从手册里抹掉，所以宁可漏判。首尾空白和句末标点会被忽略（模型很爱补个句号）。

为什么是**教练**表态而不是两人一致：教练是这个结构里的挑战者（人格里写死
「你的任务不是附和，而是挑刺」）。挑刺的人没刺可挑了，这场辩论才真的到头；
营养师是方案提出方，不该主动认输。所以这条纪律只写进教练的人格。

三道保底：

1. `society.MIN_ROUNDS = 2`——第 1 轮是「教练挑刺 + 营养师回应」，是结构上最小的
   有效交锋，不许砍。
2. 收手那轮的发言**先记录再判断**，一个字都不丢。另外 `RolePlaying.step()` 一轮往返
   中途掐不断，所以收手总落在**轮次边界**上，记录里每一轮都是完整对称的。
3. `--no-converge`（命令行）/ 网页上「谈拢了就收手」复选框，一键回到死板跑满。

**mock 模式下恒关**（`pipeline` 里 `early_stop = converge and not mock`）。ScriptedBackend
只吐固定模板、本来也说不出那句话，但显式关掉更清楚：mock 的职责就是证明循环确实
跑满了 N 轮。`pipeline` 是唯一把「mock」翻译成「关掉收手」的地方，`society` 只认
`early_stop`，它不认识 mock。

> 顺带记一笔：`society.py` 里 `if assistant_response.terminated or ...: break` 这行
> **在我们这套配置下永远不会触发**。camel 的 `ChatAgent` 默认不装任何
> `response_terminator`，那个 `terminated` 只在「上下文超限」和「外部 stop_event」
> 两种情况下为真，我们两条都没用上。它现在是一条保留的安全网，不是收手机制。
> （也正因为这样，我们没走 camel 自带的 `ResponseWordsTerminator`：它的「包含即
> 终止」会把一整段发言丢掉，而且 `RolePlaying` 在终止路径上会把 `user_response.msgs`
> 清空，我们连原文都拿不到，没法校验。）

> **关于整理环节**：`digest.py` 不是第三位智能体。它没有独立人格、不参与讨论，
> 只做格式压缩，并被硬性要求「不得添加对话里没有的观点」。
> 手册里的每一个观点都来自两位教练的发言。

## 二、目录结构与模块职责

```
camel-fitness-nutrition-duo/
├── README.md
├── docs/ENGINEERING.md         # 本文件
├── pyproject.toml              # 依赖与入口；含 mcp<2 的强制约束（见第八节）
├── .env.example                # 复制成 .env 后填 key
├── src/fitness_duo/
│   ├── personas.py             # ★ 两个人格设定
│   ├── topics.py               # ★ 议题表（= 手册大纲）
│   ├── profile.py              # ★ 读者档案：目标/处境预设、身体情况、定制手册的输入
│   ├── society.py              # ★ CAMEL RolePlaying 编排
│   ├── fooddata.py             # ★ 原料成分表 + 两位教练的查表工具
│   ├── digest.py               # 对话 → 手册 → 一页速查
│   ├── pipeline.py             # ★ 完整流程编排（cli 与网页共用同一套）
│   ├── backends.py             # 离线模拟后端（BaseModelBackend 子类）
│   ├── config.py               # 模型工厂
│   ├── cli.py                  # 命令行入口
│   └── data/
│       └── food_composition.csv  # 146 条食物成分，每行可回原出处（见第四节）
├── launcher.py                 # 网页启动器（纯标准库，见第六节）
├── make_shortcut.py            # 在 Windows 桌面生成双击快捷方式
├── run.sh                      # 命令行的一键脚本
├── tools/
│   └── build_food_table.py     # 重建上面那张 CSV（见第四节）
├── tests/
└── outputs/                    # 运行产物
```

`pipeline.py` 是编排的唯一出处：`cli.py` 把它的回调接到 `print` 上，`launcher.py`
把同一批回调接到网页的 SSE 广播上。所以命令行和网页不会各跑出一套行为。

## 三、手册里有什么

六个议题对应六节，最后一节是附录：

1. **先定基准：热量与蛋白质** — 要不要称重算卡路里
2. **训练日和休息日，吃法要不要变** — 碳水放在什么时间吃
3. **增肌与减脂：热量怎么设，肌肉怎么保** — 速率控制与代谢适应
4. **真实场景生存指南** — 外卖、食堂、加班、便利店、火锅局
5. **补剂红黑榜与常见误区** — 哪些值得买，哪些是智商税
6. **附录 A/B/C** — 双教练分歧备忘、红线信号、每日自检清单

其中**附录 A 是这个项目最有价值的部分**：单人写方案时，
「这里我其实没想清楚」会被无意识地抹平；双人格对话则会把它暴露出来。
手册如实保留了两人始终没谈拢的点，并写明各自立场，让读者自己选。

如果填了读者档案（见第五节），手册开头还会多一块**《你的档案》**——
由代码生成、不是模型写的，列出你填的目标、处境、身体情况，
以及按它们换算出的 BMI、蛋白质克数区间和每周安全变化速率。
这块是**输入**不是结论，手册里明确写着「以正文为准」。

### 一页速查版

完整版很详细，实际用起来会发现大部分时候用不到那么多。所以每一轮**额外产出一份
速查版**（`outputs/quick-<时间戳>.md`），只留最常用的一页：

- **你的数字** —— 每天要盯死的那几个量（热量、蛋白质、每周体重变化）
- **每天就这么做** —— 5–8 条，以动词开头
- **做不到的时候** —— 外卖、加班、食堂、应酬场景下的兜底动作
- **红线** —— 必须停下来去看医生的信号

三条设计上的讲究：

1. **它的输入是拼好的完整手册，不是对话。** 压缩这一步没有任何新信息可加，
   于是速查版里不可能出现完整版没有的说法，两份文件也不会互相矛盾——
   这是这个功能唯一真正重要的不变量，测试里专门钉了一条。
2. **免责声明跟着它走。** 「一页纸」正是它最容易被单独打开、单独转发的原因，
   所以那句话不能只留在完整版里。
3. **完整版一个字都没动。** 两份同时交付，速查版只是多花一次模型调用
   （约占总调用数的 2%）；模型没吐出东西时就不落这个文件，
   命令行和页面都不会提一个不存在的路径。

在网页上它是**排在第一屏**的那一份：点开「手册」先看到速查版，完整版在它下面，
两个版本各有自己的下载按钮。

## 四、成分表：手册里的营养数字从哪来

加了成分表之前，手册里的食物建议长这样：

> 便利店两个茶叶蛋加一盒无糖酸奶，蛋白质约 25 g。

这句话读起来挺具体，但**没有一个数字是查得到的**——全是模型凭记忆估的。
问题不在于它估得离谱，而在于估错了没人能发现：读者照着买照着吃，
也不会有人去核对。这是「手册很虚」的真正原因。

### 做法：给表，同时立纪律

光把表塞给模型没用，它照样会凭记忆说数。所以两件事一起做：

1. **两位教练各配两个工具**（`fooddata.py`）：
   - `lookup_food(name)` — 查某种食物每 100 克的营养，返回现成数字
   - `search_food(keyword)` — 只列名称，用来确认「表里有什么」
2. **人格里写死查表纪律**（`personas.py`）：发言里凡是要出现具体食物的
   营养成分，必须先查表；查不到就直说「成分表里没有」，**不许凭记忆编**。
   教练还多一条权力——可以拿表抽查营养师报的数字。这是把「挑刺」
   从观点层面延伸到事实层面，正好是双人格结构擅长的。

效果是手册里这类句子：

> 两个茶叶蛋（按 100 g）13 g 蛋白 / 139 大卡，150 g 无糖酸奶 4.2 g 蛋白 / 129 大卡，
> 100 g 便利店鸡胸 24.6 g 蛋白 / 118 大卡，合计 41.8 g 蛋白、386 大卡。

每个数字都能在表里查到，且查不到的地方会如实写「成分表里查不到，只能看包装标签」。

### 表里有什么

`src/fitness_duo/data/food_composition.csv`，146 条，字段：
`name / alias / category / edible_pct / energy_kcal / protein_g / fat_g / carb_g /
fiber_g / sodium_mg / source / src_code`。覆盖蛋白来源、主食、常见蔬果、
菌藻、坚果油脂。`protein_g` 等一律是**每 100 克可食部**。

原书的占位符（`Tr` 微量、`—` 未测定、`un` 未知）统一写成人能用的 0，
数字尾巴上的 `*`（表示计算值）也一并去掉——留着原样会让 CSV 的列一半是字符串
一半是数字，Excel 里没法排序。

**数据来源有两处**，`source` 列逐行写明：

- **绝大多数**取自《中国食物成分表标准版(第6版)》「能量和食物一般营养成分」，
  `src_code` 是原书食物编码；
- **少数几条**取自 USDA FoodData Central（公有领域），带 `fdcId` 可在
  fdc.nal.usda.gov 直接查。补的是那份 OCR 版缺失、且**成分跨地区稳定**的
  单一原料食物（蓝莓、纯芝麻酱）。

配方类产品（面包、花生酱）**故意不补**：美国花生酱普遍加糖和氢化油、
美式面包和中式面包差得远，拿美国数字挂中文名就是「精确的错」。
这类东西的正确回答是「查不到，看包装背标」——而背标恰好是读者唯一能
拿到准确数字的地方。

要重建这张表：

```bash
python3 tools/build_food_table.py     # 只依赖标准库，不需要装项目依赖
```

> **授权注意**：上游数据取自社区 OCR 仓库
> [Sanotsu/china-food-composition-data](https://github.com/Sanotsu/china-food-composition-data)，
> 该仓库**没有 license**（等于保留所有权利）。所以本仓库只收一份按需挑选、
> 每行可回溯的派生表，不搬运上游原始文件；`tools/.cache/` 已进 `.gitignore`。
> 要把这张表用到别处之前，请自行确认授权。

### 两个刻意的设计

**一、宁可查不到，不许查错。** 匹配只允许「表名包含查询」这一个方向
（`鸡胸` 命中 `鸡胸肉`），不允许反过来。因为反方向会出一类很隐蔽的错误：
查询「蛋白粉」时，「鸡蛋白」的别名「蛋白」是它的子串，于是返回蛋清的
11.6 g 蛋白，模型还以为查到了。**查错了比查不到危险得多**——查不到模型会
换个说法重试，查错了没有任何补救机会。补剂另有一道显式拦截，
给的是「表里没有，别拿别的食物代替」，而不是硬凑一个相近的。

**二、算出来的数字交给代码。** 表里的「蛋白密度 g/100kcal」「凑够 20 g 蛋白
需要多少克」都是 `fooddata.py` 算的，不是模型算的。模型做除法和单位换算
经常出错，而且错了看不出来——这和 `profile.py` 里 BMI、蛋白质区间由代码
换算、不由模型写，是同一条原则。

## 五、定制档案的三处落点

`--goal/--crowd/--sex/--age/--height/--weight/--constraints/--notes`，
或 `--profile my.json`（命令行上显式给的项会覆盖 JSON 底稿）。

档案有三处落点，缺一不可：

| 落在哪 | 干什么 |
|---|---|
| 两位教练的 system message | 每个议题都带着「这个人」的数字吵。1.6–2.2 g/kg 这种区间才有对象 |
| 整理环节 | 把明显不适合这位读者的建议删掉或标注（忌口、伤病、作息对不上的） |
| 手册开头 | 一块**代码算出来**的《你的档案》：BMI 及分类、蛋白质克数区间、每周安全变化速率 |

关于最后一块，有两点要说清楚：

- 这些数字是**换算起点，不是手册结论**。它们由 `profile.py` 按公式算出来，不在对话里，
  所以手册里写明「以正文为准」——正文才是两位教练吵出来的东西。
- 同样这几个数字也喂给了两位教练，所以他们多半会在对话里正面讨论到它。

**不填档案，行为和从前逐字一样**（文件名、终端输出、手册内容都不变）。
填了档案，文件名会多一个目标标记，比如 `handbook-20261006-204406-fat_loss.md`
——同一个 `outputs/` 下躺着好几份手册时，一眼能看出哪份是给谁的。

## 六、网页版

不想敲命令的话，有个网页界面：选议题、选轮数、看着两位教练一句句吵完，跑完直接读手册。

```bash
.venv/bin/python launcher.py            # 起服务，自动打开浏览器
.venv/bin/python launcher.py --mock     # 页面上的「模拟模式」默认勾上，不花钱
```

| 页面上有什么 | 说明 |
|---|---|
| **你的目标与身体情况** | 折叠在页面最上面，标题下面那行摘要一直显示「填了没有、填了什么」。选目标、选处境、填身高体重，右边会实时算出 BMI 和蛋白质克数。选完目标还会多出一个「＋ 加一节「…」」按钮，点了就把该目标的专属议题加进议题表（比如减脂 → 减脂平台期与饮食休息）——**点了才加，不点就不花钱** |
| 议题多选 + 轮数 | 想跑几个议题、每个**最多**吵几轮。收尾议题（分歧备忘）固定勾选、自动追加 |
| **谈拢了就收手** | 教练提不出新的反对意见时该议题提前结束，不再跑满上面的轮数。关掉它就回到死板跑满。模拟模式下恒不生效 |
| **自己加议题** | 点「＋ 添加议题」写标题和「要讨论什么」即可。另外两项（收敛目标、营养师的开场方案）选填，留空会自动补默认值 |
| **运行状态** | 脉冲的状态点 + 逐秒走的计时 + `发言 12/42` 的进度 + 当前动作（「正在生成 教练 的发言」）。真实跑一个议题要等模型几十秒，没有这些东西页面会像卡死 |
| 对话页 | 营养师（蓝）与教练（绿）的发言实时逐条出现，按议题分块 |
| 手册页 | 跑完渲染成可读的 markdown。**速查版排在完整版前面**——只有一页，看它多半就够了；要展开的做法、两人分歧、每日自检清单再往下翻。两个版本各有自己的「下载 .md」按钮，也可以「查看原文」 |
| 停止 | 在**当前这一轮结束后**收手——一轮内部是两次模型调用，掐不断 |
| 并发保护 | 两个标签页各点一次「开始」不会跑成两轮（真实模式那是在烧钱） |

自己加的议题**不会进仓库**：它们随「开始」一起发给后端，只存在这一次运行里
（页面上会记住草稿，刷新不丢，存在浏览器 localStorage）。议题描述有 400 字上限
——它每一轮都要进 system message 发给两个 agent，写长了成本是成倍翻的。

档案的草稿同样存在浏览器 localStorage 里，**只在这台机器上**；「清除档案」能把它们一起删掉。
注意档案本身会随这次运行发给模型（它就是给模型看的），并写进手册开头——
所以别往里写你不想让它出现在手册里的东西。

> 小提示：进度里的 `发言 N/M` 是按「轮数 × 议题数」算出来的**上限**，因为轮数本身
> 就是上限。某个议题提前收手（教练说了「无异议」）时，实际条数会比 M 少，
> 计数器停不到 M 是正常的——页面上会当场补一句「教练已无新意见，第 N 轮收手」，
> 别当成卡住了。

⚠️ **模拟模式的「手册」看起来会有点怪**：它没有标题层级，每条回复也几乎一样。
那是因为模拟后端不分人格、不分议题，只吐固定模板，整理环节同样如此。
这不是渲染坏了，是模拟模式本来就只能验证「管道通不通」。

跑完的产物仍然落在 `outputs/`，和命令行完全一样。中途点「停止」的话**一个文件都不写**
——半成品手册比没有手册更容易被误当成完整成果。

零新依赖，只用标准库。重复启动不会起第二个服务：第二次会认出已经在跑的那个，
只把浏览器指过去（不会开出两个各自为政的页面）。

### 双击启动（Windows 桌面快捷方式）

在 WSL 里跑一次：

```bash
.venv/bin/python make_shortcut.py
```

它会在 Windows 桌面建一个「健身饮食手册」快捷方式，双击就等于
「起服务 + 开浏览器」，不用开终端。重复双击不会起第二个服务。

几点说明：

- 快捷方式里写的是 `.venv/bin/python`（不是 `uv run`）——直接解释器秒起，
  `uv run` 每次要解析同步环境，没网时还可能卡住。
- **这个 `.lnk` 不会被提交**（`.gitignore` 挡着）：它内嵌了本机发行版名和绝对路径，
  换台机器就失效，而且这个仓库是公开的。换机器重新跑一遍 `make_shortcut.py` 即可。
- 不想要了，直接把桌面上那个文件删掉就行。
- 前提是 WSL 里能找到 `powershell.exe`（正常装好的 WSL 都有）。

## 八、踩坑记录

这四个坑都是本项目实际踩到并修掉的，照抄网上教程大概率会中招：

**1. `mcp` 版本过新会让 `import camel` 直接崩**

camel-ai 0.2.90 只声明了 `mcp>=1.3.0`，没有上界，于是装到 mcp 2.x。
而 mcp 2.x 移除了 `mcp.server.FastMCP`，camel 内部还在 `from mcp.server import FastMCP`：

```
ImportError: cannot import name 'FastMCP' from 'mcp.server'
```

`pyproject.toml` 里已锁 `mcp>=1.3.0,<2`，别删。

**2. `ChatAgent` 已经没有 `role_name` 参数了**

```
ChatAgent(system_message, model, memory, ...)   # 0.2.90
ChatAgent(role_name, system_message, model...)  # 旧教程里的写法
```

**3. `RolePlaying` 会覆盖你写的人格**

默认情况下 `RolePlaying` 会根据 `assistant_role_name` 自己生成 system message，
你辛苦写的人格设定会被丢掉。必须把构建好的 agent 显式传进去：

```python
RolePlaying(
    assistant_role_name="营养师",
    user_role_name="教练",
    assistant_agent=assistant_agent,   # ← 传了才用你的 system_message
    user_agent=user_agent,
    with_task_specify=False,           # ← 否则内部还会再建 agent
    with_critic_in_the_loop=False,
)
```

另外 `with_task_specify` 默认为 `True`，会在内部再建一个 agent 改写任务，
与「只有两位智能体」的设定不符，所以关掉。

**4. camel 默认的 token 计数器要联网下载词表，在国内会无限期挂住**

> 症状：网页上**计时器在走，但一句发言都不出来**，也不报错；终端里一条日志都没有。

`ChatAgent` 构造时会向模型后端要 token 计数器，camel 默认去建
`OpenAITokenCounter`，而它要用 `tiktoken` 加载 `o200k_base` 词表。本地没有词表时，
tiktoken 会去 `openaipublic.blob.core.windows.net` **下载**——那个域名在国内连不上，
`requests` 又没设超时，于是**卡死在建 agent 那一步**，模型请求根本没发出去。

更阴的是 tiktoken 把词表缓存在 `/tmp/data-gym-cache`（不是 `~/.cache`），
重启一次就没了。于是它的表现是「昨天还能跑，今天就不行」；而且**模拟模式一切正常**
（离线后端自带计数器，绕开了 tiktoken），很容易被误判成业务代码的 bug。
排查时用 `faulthandler` 打线程栈是最快的——栈顶会直接指到 `tiktoken/load.py:17 read_file`。

修法是给真实后端也注入一个不联网的计数器，顺带设上超时：

```python
ModelFactory.create(
    ...,
    token_counter=OfflineTokenCounter(),   # 见 src/fitness_duo/backends.py
    timeout=CALL_TIMEOUT,                  # 把「无限期挂住」变成「报错」
)
```

`tests/test_pipeline.py` 里有两条测试钉住它。注意那两条是**放进线程再加超时**跑的：
真回归时这条路径是挂死而不是抛异常，直接调用会把整个测试套件一起拖住。

## 九、测试

```bash
uv run pytest
```

目前 215 条，全部离线（用的是模拟后端，不花钱、不联网）。五个文件各管一层：

| 文件 | 条数 | 管什么 |
|---|---|---|
| `tests/test_fooddata.py` | 33 | 查表逻辑、匹配方向、CSV 数据体检 |
| `tests/test_profile.py` | 69 | 档案解析（边界值、非法值）、BMI/BMR/蛋白质区间的公式 |
| `tests/test_pipeline_run.py` | 52 | 端到端跑一遍：议题解析、落盘、定制档案、CLI 输出 |
| `tests/test_launcher.py` | 38 | 网页的纯逻辑部分：事件总线、单实例识别、请求校验 |
| `tests/test_pipeline.py` | 23 | 单元层面：人格互不相同、system message 拼装、后端注入、提前收手判据 |

几条值得知道的：

- **`test_fooddata.py` 里有一条用四大营养素反推热量的体检**：4×蛋白 + 9×脂肪 + 4×碳水
  对不上表里的 `energy_kcal`，就说明 OCR 出错。已知的出错类型是 kcal/kJ 两列标反，
  那会让热量膨胀 4.18 倍，一抓一个准。
- **`test_pipeline_run.py::test_quick_is_compressed_from_the_finished_handbook`**
  钉住了速查版的核心不变量：它的输入必须是拼好的完整手册，不是对话。
- **提前收手那组测试全靠「奇数调用都是教练」这条规律**：开场白不花模型调用，
  之后每轮先教练后营养师。`ConcedingBackend` 据此让教练在第 2 轮说「无异议」，
  于是轮数、条数、收手标志全都可复现。`test_scripted_backend_never_trips_the_concession`
  是一条表征测试——将来谁把 mock 的文案改成含「无异议」，它会先红。
- **`test_pipeline.py` 里那两条 token 计数器的测试是放进线程再加超时跑的**：
  真回归时这条路径是挂死而不是抛异常，直接调用会把整个测试套件一起拖住。
- `test_launcher.py` 只测确定性的部分（事件总线、单实例识别、请求校验）；
  「起服务 + 开浏览器 + 线程」那条整链路不做 pytest（脆且没必要），靠手工端到端点一遍。

`pyproject.toml` 里 `pythonpath = ["."]`：`launcher.py` 和 `make_shortcut.py`
在项目根、不是被安装的包（只有 `src/fitness_duo` 是），测试要 import 它们
得把根目录自己加进 `sys.path`。
